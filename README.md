# IME Indicator

> 屏幕底部的中英文输入状态提示条。切换输入法时弹一下，让你**一眼看出现在打出来的是中文还是英文**，不用低头找任务栏角落那个小图标。

**v8.3.1** · [更新说明](CHANGELOG.md) · [MIT](LICENSE)

```
┌────────────────────────────┐
│ ┃  中   中文输入             │      蓝   = 中文
│ ┃       半角                 │      琥珀 = 中文输入法内切到了英文
└────────────────────────────┘      绿   = 英语键盘
```

纯 Python 标准库（tkinter + ctypes + winreg），**无第三方依赖、单文件、绿色免安装、不联网**。

---

## 特性

- **读真实状态，不猜快捷键**。直接读前台窗口线程的输入法状态，鼠标点语言栏、点托盘输入法图标、按 `Shift`、按 `Alt+Shift`、在系统设置里改，全都能反映出来。
- **三种状态分得清**。中文输入法按 `Shift` 切到的英文，和整个语言切到"英语键盘"的英文，本来长得一模一样；这里用**颜色 + 文案**区分开。
- **切换窗口也能提示**（可选）。Windows 是「每个窗口各自记住输入法」的，切过去先看一眼很实用。
- **快，而且不自己制造卡顿**。60ms 轮询 + 键盘钩子加速；中文布局一次采样约 0.2ms，英语布局 **0 次跨进程调用**（约 0.01ms）。
- **无边框全屏游戏里不再判错**。以前在游戏窗口上读一次要 12–18ms 却只给 10ms 超时，实测 20 次里只有 4 次读全，提示条在「中文 / 未知」之间乱跳。现在按语言短路 + 60ms 超时，读不到就保持旧状态。
- **全屏判定是真的准**。`SHQueryUserNotificationState` + 窗口几何（贴满显示器且无标题栏），独占全屏、无边框全屏都认得出来，判定依据会写进日志。
- **静默的时候是真静默**。`pause` 策略下停采样、**卸掉全局键盘钩子**、收起提示条。
- **不重复弹**。新应用启动那几百毫秒的瞬态会被状态机吃掉：读不到不算变化、候选状态要稳定 200ms 且被看到两次、换窗口后 250ms 内不弹。
- **托盘常驻**。右键可切常驻显示、透明背景、开机自启、日志，也能打开图形化设置窗口。

## 它识别什么

| 项 | 是否识别 | 说明 |
|---|---|---|
| 中文 / 英文 | ✅ 始终准确 | 英语键盘直接由 HKL 判定（不碰 IMM）；中文键盘读 `open` + 转换模式的 native 位 |
| 输入语言（中文键盘 / 英语键盘） | ✅ 始终准确 | 读前台窗口线程的键盘布局（HKL） |
| 全角 / 半角 | ⚠️ 分输入法 | 搜狗等会上报 `IME_CMODE_FULLSHAPE`；**微软拼音不上报**（两种宽度都是 `0x401`）。不上报时用 `Shift+Space` 推断，并按 HKL 记住结论 |
| 大写锁定 | ✅ | 默认不提示，可在设置里打开 |
| 是哪个输入法 | ❌ 不识别 | 见下文「为什么不显示输入法的名字」 |

### 三种状态能一眼分开

中文输入法按 `Shift` 切到英文之后，和真正切到「英语键盘」看起来完全一样——都是打英文。但从系统角度看，这是两件不同的事：

| 显示 | 颜色 | 含义 | HKL | IMM |
|---|---|---|---|---|
| `中  中文输入` | 蓝 | 打得出中文 | `0804` | native |
| `EN  英文 · 输入法内` | 琥珀 | 同一个中文输入法，按 Shift 关了 | `0804` | 非 native |
| `EN  英文 · 英语键盘` | 绿 | 整个语言切到英语键盘了（Alt+Shift） | `0409` | — |

前两行的键盘布局**完全相同**，只看 IMM 是分不出来的，必须同时读 HKL 的 `langid`。`--once` 会把两者都打印出来。

全角时下面那行会变成橙色的 `● 全角`。**英语键盘下没有全角这个概念**，那行固定显示 `无全角`，按下 `Shift+Space` 也不会被当成切换全角——否则会弹出一个实际并不存在的变化。

### 全角 / 半角是怎么判的（以及为什么它"不稳"）

转换模式里有一位 `IME_CMODE_FULLSHAPE (0x8)`，问题是这一位**不是所有输入法都写**：

| 输入法 | 半角 | 全角 | 能直接读吗 |
|---|---|---|---|
| 搜狗 | `0x401` | `0x409` | ✅ |
| 微软拼音 | `0x401` | `0x401` | ❌ 两种宽度一样 |

（InputTip 干脆不做全角，它的 issue #77 从 2024 年开到现在。）这里的做法是**每个键盘布局学一次**：

1. 按下 `Shift+Space` 时先按"翻转"立刻显示，不等输入法。
2. 1.2 秒内看 `FULLSHAPE` 位有没有跟着翻。
3. 翻了 → 这个输入法会上报；结论写进 `config.json` 的 `ime_caps`，以后直接读这一位。
4. 没翻 → 这个输入法不上报；以后用推断值，直到你再按一次 `Shift+Space`。

所以**第一次**按 `Shift+Space` 会看到一次"先猜再校准"的过程，之后就是准的。换了输入法（HKL 变了）会重新学一遍。

如果哪天学错了（比如切窗口时不同线程的 `conv` 不一样），下一次按键会发现"这一位没动"，自动改判成"不上报"并补上这次显示——不会永久静默。

### 为什么不显示输入法的名字

同一种语言（`zh-CN`）下装了多个中文输入法时，**Windows 不向外部程序暴露"当前是哪一个"**：

- 键盘布局 HKL 完全一样；
- 注册表 `InputMethodOverride` 只在系统设置里改默认输入法时才更新，日常切换不跟手；
- TSF 的 `GetActiveProfile()` 只反映调用线程自己的状态，后台进程拿到的是进程启动那一刻的值；
- 输入法自己的辅助窗口大多不可见（微信输入法、微软拼音根本不建窗口，豆包的窗口 `IsWindowVisible` 恒为 false）。

早期版本为此写过近千行探测代码（TSF、注册表、窗口指纹、手动指定、按语言猜），实测仍无法稳定区分，于是整层砍掉，只保留唯一被验证可靠的检测链路。

> **建议只安装一个中文输入法。** 装了两个时提示条依然正确（它只回答"中文还是英文"），只是不会再告诉你是哪一个。这在绝大多数场景下够用。

## 快速开始

**需要** Windows 8 及以上，Python 3.8+（要带 tcl/tk，python.org 的官方安装包默认带）。

1. 下载本目录全部文件，放到任意位置（建议固定一个目录，别放临时文件夹）。
2. 双击 `StartIMEIndicator.bat`，托盘出现一个蓝色「中」图标。
3. 切换中英文试试，提示条会从屏幕底部弹出来。

| 文件 | 用途 |
|---|---|
| `StartIMEIndicator.bat` | 正常启动（无控制台窗口） |
| `StartWithLog.bat` | 启动并记录 `events.log`，排查问题用 |
| `DemoHighlight.bat` | 演示各种状态的显示效果 |
| `_find_python.bat` | 被上面三个脚本调用，自动寻找可用的 Python |

脚本会自动探测可用的 Python（`pythonw` / `python` / `py` 启动器 / 官方安装目录），找不到会给出提示。也可以直接用命令行运行，见下节。

首次使用建议右键托盘图标 → **设置...**，把停留时长和透明度调到顺手。退出：右键托盘图标 → **退出**。

> **想开机自启？** 托盘右键 → 勾选「开机自启」即可（只在你当前用户下写一条 `HKCU\...\Run`，不需要管理员权限）。
>
> **升级版本时**先退出旧实例：程序用同名互斥体挡第二个实例，托盘里还开着旧版时，双击新版会静默退出。

## 命令行

```bat
python ime_indicator.py              :: 正常启动（托盘常驻）
python ime_indicator.py --once       :: 读一次当前状态并打印，然后退出
python ime_indicator.py --debug      :: 每 200ms 打印一次采样（含 IME 原始值），Ctrl+C 结束
python ime_indicator.py --debug 30   :: 同上，30 秒后自动结束
python ime_indicator.py --demo       :: 只弹演示动画，不常驻
python ime_indicator.py --log        :: 启动时开启 events.log
python ime_indicator.py --version
```

`--once` 是排查"为什么没反应"最快的手段：

```
前台窗口: 0x208AC  Chrome_WidgetWin_1
输入语言: 0x0804  中文   HKL=0x08040804
中文: 是   全角: 否   可靠: True   来源: ime  耗时: 0.27ms
IME 原始值: conv=0x1  open=True  FULLSHAPE(0x8)=0
全屏判定: 否 (no)
大写锁定: 关
```

`来源` 那列是关键：

| 来源 | 含义 |
|---|---|
| `layout` | 英语/其他语言键盘，按 HKL 直接判定，**没有查 IMM**（所以 0.01ms） |
| `ime` | 中文键盘，`WM_IME_CONTROL` 读到了真实状态 |
| `timeout` | 中文键盘但 IME 没响应（游戏、UWP、受保护进程）。界面上会**保持上一次的状态**，不会闪成"未知" |

`IME 原始值` 那一行是给全角排查用的：在文本框里按 `Shift+Space`，看 `conv` 的 `0x8` 位变不变——变了说明这个输入法会上报，一直不变就是不上报（走推断）。

`全屏判定` 会给出判定依据：`no` / `geometry`（贴满显示器） / `quns3`（独占全屏） / `quns2+geometry`。

如果它打印 `中文: 是`，说明检测链路正常，问题在别处（例如前台是全屏游戏，被全屏策略静音了）。

## 配置

配置文件是程序目录下的 `config.json`，用设置界面改最省事（右键托盘 → 设置）。手工编辑也可以，改完重启生效。示例见 [`config.example.json`](config.example.json)。

| 键 | 默认 | 说明 |
|---|---|---|
| `duration` | `1.6` | 提示条停留秒数 |
| `game_duration` | `1.0` | **游戏里**的停留秒数（见「游戏里会不会掉帧」） |
| `always_on` | `false` | 常驻显示，不自动隐藏 |
| `margin_bottom` | `38` | 距屏幕工作区底部像素 |
| `opacity` | `0.85` | 整体不透明度 |
| `transparent_bg` | `false` | 去掉面板底色，只留文字 |
| `follow_mouse_monitor` | `true` | 显示在鼠标所在的显示器上 |
| `show_on_startup` | `true` | 启动时先提示一次 |
| `show_on_mode_change` | `true` | 中英文切换时提示 |
| `show_on_fullwidth_change` | `true` | 全角/半角切换时提示 |
| `show_on_caps_change` | `false` | 大写锁定时提示 |
| `show_on_window_change` | `false` | 切换窗口时提示（开了就是每切到一个新窗口都弹一次） |
| `show_fullwidth` | `true` | 是否显示「全角 / 半角」 |
| `poll_ms` | `60` | 检测间隔，20 / 40 / 60 / 100 / 200 |
| `hook_hotkeys` | `true` | 监听切换键，命中后立刻加速轮询（全屏游戏时自动卸掉） |
| `fullscreen_policy` | `"pause"` | 全屏时：`pause` 静默 / `reduce` 降频 / `normal` 正常 |
| `ime_caps` | `{}` | 自动学习结果：哪些 HKL 的输入法会上报全角位。不用手改 |

`show_on_window_change` 默认关闭的原因：从中文的记事本切到英文的浏览器时状态确实变了，但这不是用户主动切换，每次都弹会很烦。默认只在**同一个窗口内**变化才提示。

打开它之后的行为是「**每切到一个新窗口就弹一次**」——哪怕新窗口的状态跟刚才完全一样。这样才有"我切过去了，看一眼"的意义；只在不同时才弹的话，切两个状态相同的窗口什么都不会发生，看起来就像功能没生效。

`fullscreen_policy` 三档的实际差别：

| 值 | 采样 | 键盘钩子 | 提示条 |
|---|---|---|---|
| `pause` | **完全停** | 卸掉 | 收起，不弹 |
| `reduce` | 0.6s 一次 | 卸掉 | 仍然弹（用 `game_duration`） |
| `normal` | `poll_ms`（默认 60ms） | 保留 | 仍然弹（用 `game_duration`） |

## 工作原理

检测只有一条链路。关键点是**能不问 IME 就不问**：

```
GetForegroundWindow()                     前台窗口（壳窗口会被过滤掉）
 ├─ GetWindowThreadProcessId → GetKeyboardLayout(tid)
 │    langid = HKL & 0xFFFF
 │      ├─ 非中文（0409 英语 / 0411 日语 …）→ 直接判"英文"，**不查 IMM**
 │      └─ 中文（0804）↓
 ├─ GetGUIThreadInfo(tid).hwndFocus       真正有焦点的控件（不是顶层窗口）
 └─ ImmGetDefaultIMEWnd(hwnd)
      └─ SendMessageTimeoutW(WM_IME_CONTROL,
             IMC_GETOPENSTATUS / IMC_GETCONVERSIONMODE,
             SMTO_ABORTIFHUNG, 60ms)
           成功与否只看 SendMessageTimeout 的返回值
           conv & 0x1 = 中文（native）   conv & 0x8 = 全角
```

**语言和状态是两条独立的线**：语言来自 HKL（切中文/英语键盘时变），状态来自 IMM（中文输入法内按 Shift 时变，HKL 不动）。两者交叉才得出上表那三种情况。

几个踩过的坑，留作参考：

- **`ImmGetContext` 不能跨进程**。实测对本机任何外部进程窗口都返回 `NULL`（包括同权限级别的 Chrome）——输入上下文在对方进程里。开源项目（InputTip、im-select、ImeModePersistence）也都只用 `ImmGetDefaultIMEWnd` + `WM_IME_CONTROL`。
- **`WM_IME_CONTROL` 的返回值不能当成功判据**。英文状态的转换模式就是 `0`，和"调用失败"长得一样；只能看 `SendMessageTimeout` 自己有没有返回。
- **超时要给够**。普通窗口约 0.2ms，无边框全屏游戏 12–18ms。给 10ms 时 25 次里只成功 15 次；给 60ms 后 25/25。
- **英文布局下不查 IMM**。HKL 已经说明那个窗口没有中文输入法，跨进程消息纯属浪费——这条让游戏里每次采样从 13ms 降到 0.01ms。
- **必须查焦点控件**。只查顶层窗口，很多程序返回线程默认值（恒英文）。
- **轮询而不是等通知**。`WM_INPUTLANGCHANGE` 只投递给有焦点的窗口，后台隐藏窗口永远收不到（实测一整晚 0 次）。
- **键盘钩子只提速，不检测**。`Alt+Shift` / `Ctrl+Shift` / `Win+Space` 命中时把轮询间隔临时降到 20ms。回调里不做任何 I/O 和跨进程查询——Windows 会因回调超时静默卸载钩子。只在**按下**时触发（以前连 `WM_KEYUP` 也处理，一次按键会触发两遍）。
- **噪声窗口过滤**。点任务栏、开始菜单、桌面时前台会瞬间变成壳窗口，输入状态恒英文。这类窗口沿用上一次真正应用窗口的结果。
- **全屏判定不能只看 `SHQueryUserNotificationState`**。它只有独占全屏才返回 `3`；无边框全屏通常返回 `2`（忙碌），而 `2` 还会被覆盖层误报。所以 `2` 必须配几何证据。几何判定用 `GetWindowRect` vs `GetMonitorInfo().rcMonitor`（同一条虚拟化坐标系），**不要**混用 `DwmGetWindowAttribute`——它返回物理像素，本机 125% 缩放下是 2560×1440 vs 2048×1152，永远比不上。
- **每次弹出都少做一次系统调用**。`resize` 会重建 DWM 重定向表面，`lift` 会改 z 序，`geometry` 会触发重排，写 `alpha` 会改合成参数。现在宽度启动时算成固定值、位置缓存、`alpha` 只在变化时写一次。

## 游戏里会不会掉帧（实测）

会。而且这件事**不是脚本能"优化"掉的**，是呈现链路的问题。以下是本机（Windows 11、无边框全屏 Minecraft、2560×1440、AMD 显卡）实测。

### 四相切屏实验

每 5 秒切一次状态，每秒截一帧读游戏内帧数，跑两轮：

| 相位 | 前台 | 提示条 | 帧数 | 说明 |
|---|---|---|---|---|
| A | 游戏 | 无 | **117–119** | 基线 |
| B | 游戏 | **有** | **63–67** | 掉约 45% |
| C | 屏幕外的空窗口（游戏失焦） | 无 | **30** | Minecraft 自己的失焦上限 |
| D | 屏幕外（失焦） | 有 | **30** | 已经限到 30，叠加层不再有额外影响 |

### 结论一：不是"被切到后台"

游戏真的失焦时是 **30 帧**（一个非常干脆的台阶），而提示条弹出时是 **63–67**，既不是 118 也不是 30。C 和 D 完全一样，也说明"失焦"和"有窗口压着"是两个独立机制。

### 结论二：DWM 合成 + AMD 帧生成

只要有一块可见窗口压在游戏上方，DWM 就没法让游戏走**独立翻转（independent flip）**，只能改走合成。微软术语表写得很直白：独立翻转是"完全绕过 DWM"，合成是"less efficient"。[ForceComposedFlip](https://github.com/fernandoenzo/ForceComposedFlip) 这个项目就是靠一个 **1×1 的隐形置顶窗**来强制游戏退出独立翻转——和我们的实验完全一致：窗口大小、透明、样式都不重要，"存在"才重要。

在 AMD 显卡上还叠了一层：**帧生成（AFMF）会在任何窗口压上来时直接 disengage**。118 → 63 正好是"生成出来的那一半没有了"，回到真实帧率。驱动侧行为，应用层没有 API 可以请求它别关；Discord 覆盖层、Steam 覆盖层、甚至系统音量条都会触发同样的事。

所以这跟渲染怎么写无关：DComp、D2D、GDI 都一样，因为它们都是"另一个窗口"。真正零成本的叠加层（RTSS、Special K、Steam / Discord / NVIDIA overlay）全部是**注入游戏进程**，像素画进游戏自己的后台缓冲，不产生第二个窗口。

### 那还能做什么

| 做法 | 效果 |
|---|---|
| `fullscreen_policy: "pause"` | **游戏里完全不弹，帧数零影响**。唯一 100% 有效的方案 |
| 给 Minecraft 单独关掉 AFMF | 断崖消失，但只剩 DWM 合成的那部分开销 |
| 提示条放第二块显示器 | AFMF 按输出生效，副屏不影响游戏输出 |
| 做进游戏里（客户端 mod 画 HUD） | 唯一"不产生第二个窗口"的做法，等于另开一个项目 |
| 就用 `reduce` / `normal` | 接受弹窗那 1 秒的掉帧，消失后会恢复 |

已经做的缓解（只影响"弹那一下"，救不了上面那条）：`game_duration` 缩短停留、游戏内不做淡出、游戏内不加速轮询、去掉每次弹出的 `resize`/`lift`/`geometry`/`alpha` 写入。

## 隐私

这个工具会全局监听键盘，所以有必要说清楚它到底做了什么：

- **不联网**。代码里没有任何 socket / HTTP / 更新检查，断网照常工作。
- **不记录输入内容**。键盘钩子只读按键的虚拟键码（`vkCode`），用来判断"是不是 `Alt+Shift`、`Shift+Space` 这类组合键"，**不缓冲、不解析、不落盘任何字符**，也不关心你在哪个程序里输入。
- **不截屏、不读剪贴板、不访问网络位置**。
- **写注册表只有一处**：勾选「开机自启」时在 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 写一条自己的路径，取消时删掉，不需要管理员权限。
- **本地文件只有三个**：`config.json`（你的设置）、手动开启日志时的 `events.log`、崩溃时的 `crash.log`，都在程序目录下，随时可删。

## 常见问题

**启动后托盘图标闪一下就没了？**
用 `StartWithLog.bat` 启动，然后看程序目录下的 `events.log`；如果出现 `crash.log`，里面是完整堆栈。最常见的原因是没有装带 tcl/tk 的 Python——命令行跑一次 `python -c "import tkinter"` 就能确认。

**双击新版没反应？**
托盘里还开着旧实例。程序用同名互斥体挡第二个实例，先退出旧的（托盘右键 → 退出）。

**切换输入法完全没反应？**
先跑 `python ime_indicator.py --once`：
- 打印 `中文: 是/否`（而不是 `?`）→ 检测正常，检查是不是在全屏游戏里（默认策略会静音）。
- 打印 `来源: timeout` → 这个窗口不响应 IMM 查询，多半是 UWP、游戏或受保护进程。

**全屏游戏里怎么不弹了？**
默认行为（`fullscreen_policy = "pause"`）：停采样、卸钩子、收起提示条。原因见「游戏里会不会掉帧」。想看到就把策略改成 `reduce` 或 `normal`。

**为什么第一次按 Shift+Space 会"慢半拍"？**
那个输入法会不会上报全角位要现场学一次（1.2 秒），学到的结果存在 `config.json` 的 `ime_caps` 里，之后就不用了。

**全角一直显示"半角"，按 Shift+Space 也没反应？**
跑 `--debug`，看 `conv` 的 `0x8` 位在按键时变不变：
- 变 → 会上报，检测链路正常；若界面仍不对，是 UI 层的问题。
- 一直不变 → 不上报，靠推断。若连推断也没反应，多半是你的全角快捷键不是 `Shift+Space`（有些输入法用 `Ctrl+.` 或在工具栏上点），那就推断不到。

**任务栏右下角那个图标能不能不要？**
可以，托盘右键 → 退出即可；不想让它自启就不勾「开机自启」。

**能不能显示"现在是搜狗还是微软拼音"？**
不能，原因见上文「为什么不显示输入法的名字」。这是 Windows 的限制，不是没做。

**支持 Windows 7 吗？**
不支持。用到了 Windows 8 才有的 `SHQueryUserNotificationState`。理论上可以降级兼容，但没做。

**支持多显示器吗？**
支持。默认显示在鼠标所在的那块屏幕上（`follow_mouse_monitor`）。

## 已知限制

- **独占全屏游戏下看不见**。分层窗口会被 DWM 绕过，提示条画在游戏画面之外。
- **无边框全屏游戏里弹出会掉帧**（见「游戏里会不会掉帧」），这是 DWM 合成 + 帧生成机制的固有代价，只有注入式叠加层能避免。
- **不区分具体输入法**（见上文）。
- **全角不保证**：取决于输入法是否上报那一位。
- **UWP / 部分沙盒应用**读不到 IMM 状态，会沿用上一次的状态。
- **只在 Windows 上可用**。检测依赖 IMM32 和 Win32 API，macOS / Linux 用不了。

## 卸载

1. 托盘右键 → 退出（先关掉正在运行的实例）。
2. 如果开过「开机自启」，重新启动一次并取消勾选，或者手动删掉注册表这一项：
   `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run` 下的 `IMEIndicator`。
3. 删掉整个程序目录即可，没有安装程序、没有服务、没有其他残留。
